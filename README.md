# Chest Auto Sorter（箱子自动分类）

一个 Minecraft **26.3 / NeoForge** Mod（单人游戏装一份即可，它同时提供背包面板与集成服侧的整理逻辑）：面对一排箱子，在**自己的背包界面里**勾选要参与的箱子，
先**预览**分类方案，再**确认整理**，把物品按类别在多个箱子之间重新分配。

- 没有专用快捷键，不改动原版按键：按 `E` 打开背包 → 点面板按钮。
- 所有写入都在**服务端**完成并逐条复核，客户端的勾选与视野判断**从不构成授权**。
- 写第一个槽位之前必须先落盘**恢复记录**，任何一步校验不过就**回滚**；不生成、不销毁、不丢弃任何物品。
- 界面文案全部走翻译键，中/英双语，跟随游戏语言。

当前版本 **0.1.0** · 许可 **GPL-3.0-or-later**（copyleft，衍生作品必须同样开源） · 仓库 <https://github.com/LiuyingZui/MC-ChestAutoSorter>

## 2. 安装

1. 取到 `chestautosorter-0.1.0.jar`（本仓库 Release 附件，或自行 `./gradlew build` 产出 `build/libs/`）。
2. 放进**你所用实例**的 `mods` 目录。注意版本隔离的启动器（如 PCL）：`mods` 在**版本文件夹内**，
   不是 `.minecraft\mods`；并且加载器只读 `mods` **根目录**，放进子文件夹（备份/分类目录）不会生效。
3. 启动后在日志里应能看到 `[ChestAutoSorter] constructed on 26.3 / NeoForge <你实际加载器版本>`
   与 `payloads registered (sort_request -> server, sort_result -> client)`。

## 3. 怎么用

```
站在一组箱子附近 → 按 E 打开背包 → 点「箱子分类」 → 勾选 → 「预览分类」 → 「整理所选」 → 点「关闭」
```

- **面板列出的是"面前的箱子"**：客户端在半径内扫描已加载区块中的箱子，要求同时满足
  ① 距离达标（默认 12 格，见第 6 节）② 落在相机视锥内 ③ 表面采样点至少有一个能被不被遮挡的射线命中。
  大箱（双箱）**只占一行**，一次选择关联两半，不会被当成两个容器重复读写。
- 面板头部信息：`范围`、`发现`、`已选`，以及 **`另有 N 个未列出：太远 x / 视野外 y / 被遮挡 z`**——
  为什么某个箱子没出现在列表里，会直接说明原因分类。
- 列表条目数超过可见行数（默认 5 行）时**滚轮滚动**，上下两端有钳制，不会滚出空白。
- **只有「整理所选」会改库存**：打开、刷新、勾选、全选、清空、预览都只读。
  勾选变化后旧预览失效，必须重新预览才能提交；处理中禁用重复点击。
- 鼠标上拿着物品时禁用预览/提交并提示先放回，**不会**自动塞回背包或丢弃。
- 面板是画在背包屏幕**之上的叠加层**：面板内的点击/滚轮被完整消费、**不会穿透到背后的槽位**；
  面板外的一切原版与 JEI 交互照常（含 `R` 查配方、`U` 收藏）。换屏幕、按 `E` 关闭背包、死亡都会自动收起面板。

## 4. 分类规则

九个类别：`木材` · `石材/建筑` · `矿物` · `植物` · `农作物/食物` · `生物掉落` · `红石` · `工具/装备` · `其他`。

优先级四层（前一层命中即返回）：

1. **显式物品 ID 覆盖表**（`ItemClassifier.defaultItemOverrides`）
2. **用户 Tag 规则**（为自定义规则预留）
3. **内置、已在 26.3 原版标签集里核实过的 Tag / 物品规则**（`defaultBuiltinRules`，**顺序有意义**：
   工具/装备排在矿物之前，所以铁镐不会被当成铁；原木排在树叶之前）
4. 兜底 `其他`

内置规则**只用真实存在的 Tag**，不猜、不发明标签名。原版没有合适标签的物品走第 1 层的显式 ID——
例如 `stone` / `cobblestone` / `deepslate` 系列并不在 `stone_crafting_materials` 等标签里，
所以它们被逐条列进覆盖表而不是靠标签命中。分类逻辑是纯 Java，可脱离游戏单元测试。

## 5. 哪些箱子会被跳过

服务端对客户端传来的**每一个**坐标重新解析与校验，被拒的条目会带**具体原因**回传给玩家：

| 原因 | 判据 |
| --- | --- |
| 距离过远 | 眼位到**逻辑箱体包围盒**最近点的距离 > 半径（大箱覆盖两半，任选一半结论一致） |
| 区块未加载 | `level.isLoaded(pos)` 为假 |
| 不支持的方块 | 只有**原版箱子**与**陷阱箱**（含大箱形态）受支持；桶、潜影盒、其它 Mod 容器一律拒绝并回传方块名 |
| 容器无法解析 | 拿不到 `Container` |
| 与已选大箱重复 | 同一逻辑容器被两个坐标命中 |
| 大箱结构不完整 | 另一半不是箱子方块 |
| 正在被使用 | 规范化锚点（大箱取左半）上仍有打开者 |
| 自定义名称箱子（受保护） | 重命名过的箱子默认跳过，见 `protect_custom_named` |

距离规则是本 Mod 自定的，**刻意不使用**原版的菜单有效性判断（原版是 4.5 + 4.0 缓冲、且只量到单个方块）。
玩家自定义的箱子名称**原样显示、不翻译、不修改**。

## 6. 配置

服务端配置，单人/集成服路径为 `config/chestautosorter-server.toml`：

| 键 | 默认 | 范围 | 含义 |
| --- | --- | --- | --- |
| `radius` | 12 | 1–64 | 判定"面前"的半径（格） |
| `max_containers` | 64 | 1–512 | 单次请求处理的最大逻辑容器数 |
| `cooldown_ms` | 1000 | 0–60000 | 两次被接受请求的最小间隔（下限 250 ms） |
| `protect_custom_named` | true | — | 跳过有自定义名称的箱子 |
| `allow_mixed_boxes` | true | — | 类别放不下专用箱时允许混装 |
| `debug` | false | — | 逐槽详细日志（含点击坐标等诊断信息） |

另有硬上限：单次请求候选数最多 **64**。

## 7. 预览会告诉你的三种布局

| 结果 | 含义 |
| --- | --- |
| 按类别专用分箱 | 每个类别独占箱子 |
| 类别已分摊到 N 个箱子，其中 M 个箱子合放多类 | **类别多于箱子**时的分摊结果，会说明实际落地情况 |
| 紧凑混装 | 有类别无法独占箱子时的兜底布局 |

容量不足（`需要 X 槽，实际只有 Y 槽`）、或专用布局失败且配置不允许混装 → **取消且不改动任何库存**。

## 8. 提交协议（为什么"不会丢东西"）

`SafeCommitter.commit` 的顺序是固定的：

1. **写前复核**：重读所有目标槽位并与快照逐格比对（结构变化、被别人动过库存都会在这里挡下，**未写入任何一格**）。
2. **先落恢复记录**：`ItemStack.CODEC` 编码的 SNBT 预镜像写到
   `chestautosorter-recovery/recovery-<时间戳>.snbt`（保留组件数据与超大数量）。
   **写不进去就直接拒绝整理**，返回「无法写入恢复记录，已在写入前取消本次整理（未改动任何箱子）」。
3. 按方案逐槽写入 → `setChanged()`。
4. **写后回读校验**：逐槽核对数量与物品身份（含组件）。
5. **全局守恒校验**：比对写入前后的 `{物品身份 → 总数量}`，任何增减都判失败。
6. 第 3–5 步任一失败 → **回滚**到快照，并**校验回滚本身**；提示语区分
   「已回滚；回滚校验：通过」与「已回滚；回滚校验：失败（严重，请保留日志）」。

全程在服务器线程执行。恢复记录是**人工恢复辅助**，不会自动回放。

需要 OP 权限：

| 命令 | 作用 |
| --- | --- |
| `/chestautosorter status` | 打印当前生效的半径/容器上限/冷却/保护改名/允许混装/debug |

## 10. 已知限制与未验证项

**限制（设计如此）**

- 不支持专用服务器（第一版）。
- 只支持原版箱子与陷阱箱；桶/潜影盒/Mod 容器会被明确跳过。
- 面板宽度上限 168 GUI 像素、屏幕内居中；画布很窄时收缩到下限 112，垂直空间不足时**减可见行数**（默认 5 行，最少 1 行，配合滚动）而不是缩按钮或缩点击区。

**未验证（不要当成已验收）**

- GUI scale **≥5**、超宽比例（21:9）、全屏下的排版未取样（已实测 scale 1/2/3/4）。
- 与 **Mouse Tweaks** 共存、**>99 超量堆**（All Stacks Infinite 环境）本轮未重跑。
- 回滚**本身失败**（`restore()` 返回 false）没有强制测试覆盖。
- 视野判定自建视锥、不注入渲染管线，因此对 Sodium/Iris 类渲染 Mod 依赖很小——这是**源码层面**的结论，未做像素级实测。

已实测的兼容性环境：开发客户端装有 **JEI 31.7.0.45**、**Inventory Profiles Next 2.3.8 + libIPN**、
**mezz_config**、**All Stacks Infinite 10.0.1**；面板与背包共存、JEI 热键、面板内不穿透、滚动、
过滤原因显示均有截图与日志留证。

## 11. 构建与测试

```bash
./gradlew test                 # 纯逻辑单元测试
./gradlew runGameTestServer    # 游戏内 GameTest
./gradlew build                # 产出 build/libs/chestautosorter-0.1.0.jar
./gradlew runClient            # 开发客户端
```

- **工具链**：Java 25（`java.toolchain.languageVersion = 25`）。
  NeoForge 的源码生成/资源处理（NFRT）固定跑在 **Java 21** 上，
  因此 `gradle.properties` 里的 `org.gradle.java.installations.paths` 指向了本机 `.tools/jdk-21…`；
  换机器时删掉这一行、或改指向你自己的 JDK 21 即可。
- **发布 jar 真机加载**：`./gradlew runClient -PreleaseJar` 会清空 `MOD_CLASSES`、
  把开发输出从 classpath 上过滤掉，并把 `build/libs/*.jar` 临时拷进 `run/mods`（跑完删除）。
  自证锚点是日志里的 `[releaseJar] MOD_CLASSES=[] devOutputsOnClasspath=0[]` 与
  `codeSource=file:/…/run/mods/chestautosorter-0.1.0.jar`。
- **发布产物不含测试脚手架**：jar 排除 `com/chestautosorter/gametest/**` 与 `com/chestautosorter/client/UiHarness*`；
  游戏测试注册靠"检查自身 codeSource 里是否存在该条目"来判定，而不是 `Class.forName`。
- `tools/*.ps1` 是无人值守取证脚本（前置窗口、模拟点击/滚轮/按键、裁剪截图、校验发布 jar、正常关窗释放 `session.lock`）。

测试基线（截至 0.1.0）：单元测试 **29 项**、`runGameTestServer` **`All 14 required tests passed :)`**。

## 12. 仓库结构

```
src/main/java/com/chestautosorter/
├── CAS.java, ChestAutoSorter.java     # Mod 入口、配置与网络注册
├── client/                            # 背包叠加层面板、按钮、输入路由、视野选箱
├── config/                            # chestautosorter-server.toml
├── core/                              # 纯逻辑：分类、聚合、规划（可脱离游戏测试）
├── diagnostic/                        # 日志、诊断命令、恢复记录
├── network/                           # C2S 请求 / S2C 结果载荷与翻译键封装
└── server/                            # 校验、快照、安全提交器、回滚
src/main/resources/assets/chestautosorter/lang/{zh_cn,en_us}.json
src/test/java/…                        # 单元测试
tools/                                 # 无人值守取证脚本（前置窗口、模拟输入、裁剪截图、校验发布 jar）
```

`run/`、`build/`、`reports/`、`snapshots/`、`release/`、`docs/` 已在 `.gitignore` 中排除：
前几个是开发客户端工作目录与本机取证留底（存档、截图、运行日志、diff、发布 jar 副本），
`docs/` 是个人机器的环境审计与逐阶段工作日志；发布 jar 请走 GitHub Release 附件。
